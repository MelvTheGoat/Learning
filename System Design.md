# Part 4: System Design

System design interviews test something different from the earlier sections — not "do you know the concept" but "can you make trade-offs out loud, under time pressure, with someone watching." The structure that works across almost every question here: clarify scale and constraints first, sketch the high-level architecture, then go deep on the one or two components the interviewer is actually probing. Don't design in silence — narrate the trade-off at each decision point.

## AI-Specific System Design

**Q1. Design a RAG-based customer support system for a company with 100,000 documents, expecting 10,000 queries per day.**
Clarify first: how often does the corpus change, what's the acceptable answer latency, and is there an existing support team whose tickets can seed a golden eval set. Architecture: offline ingestion pipeline (extract, structure-aware chunk, embed) writing to a hybrid index — dense vectors in a vector DB (Pinecone/Weaviate/pgvector depending on ops preference) plus a BM25 index for exact-term queries. At query time: embed the question, retrieve from both indices, fuse with RRF, optionally rerank the top candidates with a cross-encoder, assemble a grounded prompt with citation instructions, generate, then run an output guardrail checking citation validity before returning. Add a feedback loop (thumbs up/down, or ticket escalation as an implicit negative signal) feeding back into the golden eval set over time. At 10,000 queries/day (roughly 7/minute average, with real peaks), this is comfortably within a single well-provisioned retrieval + generation pipeline — the interesting design pressure is corpus freshness and citation trustworthiness, not raw query throughput.

**Q2. Design a system to detect and prevent hallucinations in a production LLM application.**
Layer defenses rather than relying on one: at the prompt level, explicit grounding instructions and a required refusal token when context doesn't support an answer; at the output level, a post-generation groundedness check that verifies each claim against retrieved source text (via an LLM judge or lexical/semantic overlap) before the response reaches the user; for high-stakes domains, a second, independent verification call using a different model or prompt, since a single model's own self-check shares that same model's blind spots; and a citation-validity check that strips or flags any cited source not actually present in what was retrieved. Continuously monitor a sampled hallucination rate in production, not just at launch, and feed confirmed hallucination cases back into the golden eval set as permanent regression tests.

**Q3. Design an LLM-powered content moderation system that needs to process high volume with low latency.**
Two-tier architecture: a fast, cheap first-pass classifier (a small fine-tuned model or even a traditional classifier) handles the large majority of clearly-safe or clearly-violating content at low latency and low cost; only genuinely ambiguous cases — those near the classifier's decision boundary — escalate to a more expensive, more capable LLM call for nuanced judgment. This routing pattern is the key design decision, since running a large general-purpose LLM on every single piece of content at high volume is both slow and expensive for a problem where most content isn't actually ambiguous. Layer in policy-category-specific detection (different harm types need different signals) rather than one monolithic "is this bad" score, cache repeated or near-duplicate content aggressively, and maintain human review for edge cases and for auditing the automated system's decisions over time.

**Q4. Design a system for an AI coding assistant that suggests code completions in real time.**
The dominant constraint here is latency, not quality — a completion arriving after the developer has already typed past that point is worse than useless. Architecture: a smaller, faster, often locally-cacheable model for the common case of short, in-flow completions, with a larger model reserved for explicitly-requested, longer generations (a full function on demand) where the user is willing to wait. Aggressive caching of common completions and of the repository's own context (so re-sending the entire file on every keystroke isn't necessary — incremental context updates instead). Debouncing/cancellation logic so a request for an in-progress line is aborted the moment the user types past it, rather than wasting compute completing a suggestion nobody will see. And a feedback signal from acceptance/rejection of suggestions, both as a product metric and as fine-tuning data over time.

**Q5. Design an AI agent system for automating customer support ticket resolution end-to-end.**
Start conservative: v1 should be assistive, not autonomous — the agent drafts a resolution and cites the reasoning/sources, a human support agent reviews and sends, and the human's accept/edit/reject action is logged as the actual measurement of whether the system is working, alongside resolution-time reduction. Only once that shadow-mode data shows strong agreement (a defined threshold, e.g. 85%+ direct acceptance with no material edits) does autonomous handling for a narrow, well-defined ticket category become justifiable, gated by explicit categorization (route only clearly low-risk, high-confidence ticket types to full automation) and a human escalation path for anything the agent isn't confident about. State kill criteria upfront: if acceptance rate or resolution-time improvement doesn't clear the bar within a defined evaluation window, the automated path is rolled back, not iterated on indefinitely.

**Q6. Design a caching strategy for an LLM-powered application to reduce cost and latency.**
Multiple cache layers, each catching a different kind of repetition. Exact-match response caching for genuinely identical requests (same prompt, same parameters) — cheap and safe, but catches only true duplicates. Semantic caching, matching new queries against previously-cached queries by embedding similarity above a threshold, catching near-duplicates and common rephrasing — more cache hits, but requires careful threshold tuning to avoid serving a stale or subtly-wrong cached answer for a genuinely different question. Prompt caching (provider-level, for the static/shared portion of a prompt — system instructions, a large fixed document) to avoid reprocessing identical context tokens on every call. And embedding caching for any content that gets embedded repeatedly (documents that don't change between requests). Cache invalidation policy has to be explicit and tied to source-data freshness requirements, not left implicit.

**Q7. Design an evaluation and monitoring system for an LLM application running in production.**
Two distinct subsystems working together: offline evaluation, running the current model/prompt version against a versioned golden set on every change, gating deployment via CI, with per-category metrics (not one aggregate) and defined regression thresholds. Online monitoring, tracking real production traffic — sampled groundedness/quality scores via a lightweight judge on a rolling sample (scoring every single production request is usually too expensive), explicit user feedback signals, latency and cost per request, and drift detection on the query distribution itself (are people asking fundamentally different kinds of questions than the golden set represents). Both feed into the same failure taxonomy and the same golden set — a production failure discovered via monitoring should become a new offline regression test, closing the loop.

**Q8. Design a system that lets multiple teams within a company share a common LLM infrastructure, with per-team cost and access controls.**
A gateway/proxy layer sitting between all internal callers and the actual model providers, rather than each team calling providers directly. The gateway handles: authentication and per-team API keys, per-team and per-environment rate limiting and hard spend caps enforced at the gateway (not hoped for downstream), usage logging tagged by team/project for cost attribution, a shared prompt-caching layer so common context isn't redundantly reprocessed across teams, and centralized model routing so a provider outage or rate-limit can fail over without every individual team's code needing to handle it. This centralizes exactly the operational concerns (cost control, observability, provider abstraction) that are wasteful to reimplement per-team, while leaving each team free to build their own application logic on top.

**Q9. Design a personalized recommendation system that combines collaborative filtering with an LLM for cold-start users.**
Standard collaborative filtering (matrix factorization, or a learned embedding-based approach) handles users and items with sufficient interaction history well and cheaply — this should be the default path for the majority of established users. For cold-start users (new, with little or no interaction history) where collaborative signals don't exist yet, use an LLM to reason over whatever explicit signal is available — a stated preference, a small onboarding survey, item metadata/descriptions — to generate an initial set of recommendations or a preference embedding that can bootstrap the user into the collaborative system once enough real interaction data accumulates. This hybrid avoids the trap of using an expensive LLM call for every recommendation request when a cheap, well-understood method already works well for the majority case.

**Q10. Design a system to detect prompt injection attacks in a customer-facing LLM application.**
Layered, not a single filter: an input-side heuristic/pattern-based screen (as a cheap first pass, catching known common injection patterns like "ignore previous instructions"), explicit in the system prompt separating trusted instructions from untrusted user input with clear delimiters so the model has structural signal about what's an instruction versus what's data, and — for applications where the LLM reads external content (web pages, documents, tool outputs) — treating that external content as untrusted input requiring the same scrutiny as direct user input, since injected instructions can arrive indirectly through content the agent reads rather than only through the direct chat box. Log and monitor blocked/flagged attempts to catch new attack patterns over time, and be honest in the design about what this layer can and can't guarantee — a heuristic filter reduces risk, it doesn't eliminate it, especially against a genuinely sophisticated attacker.

**Q11. Design a system for real-time translation with strict latency requirements (under 200ms).**
At this latency budget, a full generate-then-return LLM call is often too slow if generation is lengthy — favor streaming output token-by-token so the user sees translation begin immediately rather than waiting for the complete response, and consider a smaller, faster, translation-specialized model over a large general-purpose one, since translation is a narrower task that doesn't need frontier-model general reasoning capability. Pre-warm and keep models resident rather than cold-starting per request. For predictable, high-volume language pairs, consider a dedicated fine-tuned or distilled model per pair rather than one large multilingual model handling everything, trading some flexibility for consistently lower latency on the common cases.

**Q12. Design an LLM-based system for automatically generating and validating unit tests for a codebase.**
Generation: feed the LLM the function/module to test plus its existing documentation and any related code for context, prompt for tests covering both the happy path and edge cases explicitly (empty input, boundary values, error conditions) rather than relying on the model to think of edge cases unprompted. Validation is the harder half and the part interviewers actually want to hear about: run the generated tests against the actual code and confirm they pass, then — critically — verify the tests are actually meaningful rather than trivially vacuous (a test that always passes regardless of the implementation is worse than no test), which can be checked by intentionally introducing a bug (mutation testing) and confirming the generated test suite actually catches it. Human review remains in the loop before generated tests are merged, at least initially, since a subtly wrong test that passes CI is a worse outcome than no test at all.

**Q13. Design a system for extracting structured data (e.g., invoices, forms) from unstructured documents using LLMs.**
Pipeline: OCR/document parsing to get raw text and layout information from the source (PDF, scanned image), then an LLM call with a defined output schema (via function calling or constrained decoding) to extract fields into structured JSON, explicitly instructed to leave a field null or flag low confidence rather than guessing when a value isn't clearly present. Validate extracted values against known constraints where possible (a date field should parse as a valid date, a total should roughly equal the sum of line items) as a cheap, deterministic correctness check independent of the LLM's own confidence. For high-stakes use (financial, legal), route low-confidence extractions to human review rather than accepting the LLM's output unconditionally, and track extraction accuracy per field type over time, since some fields (a clearly labeled total) are far more reliable to extract than others (a handwritten annotation).

**Q14. Design a multi-tenant LLM SaaS platform where each customer's data must remain isolated.**
Data isolation at every layer, not just the database: separate vector index namespaces (or fully separate indices) per tenant, so a retrieval query for tenant A can structurally never surface tenant B's documents regardless of query content; per-tenant API keys and strict authorization checks on every request confirming the requesting tenant matches the data being accessed; no cross-tenant caching of responses that could leak content between tenants (semantic caching in particular needs tenant-scoping built in, not bolted on); and audit logging of every data access, tagged by tenant, both for the tenant's own compliance needs and for your own security review. If using a shared underlying model rather than per-tenant fine-tuning, confirm the provider's data usage policy doesn't retain or train on tenant prompts, since that's a data isolation boundary you don't control directly and need to verify contractually.

## Traditional System Design

**Q15. Design a URL shortener.**
Core: a mapping from a short code to a long URL, generated either via a base62-encoded auto-incrementing ID or a hash of the URL with collision handling. Write path: generate the short code, store the mapping (a simple key-value store is sufficient — the access pattern is a lookup by key, not complex queries), return the shortened URL. Read path: look up the short code, redirect (a 301 or 302 depending on whether you want the redirect cached by browsers). At scale: this is an extremely read-heavy workload, so cache aggressively (the mapping is immutable once created, making it ideal for caching), shard the key-value store by short code if a single instance can't hold the full dataset, and consider a CDN-level redirect for the most popular links to avoid hitting your own infrastructure at all for the hottest paths.

**Q16. Design a rate limiter.**
Common algorithms, each with a real trade-off: fixed window (simple counter reset every interval, but allows a burst of 2x the limit right at the window boundary); sliding window log (perfectly accurate, but memory-expensive since it stores every request timestamp); sliding window counter (a good practical compromise, approximating the sliding window using two adjacent fixed windows weighted by how far into the current window you are); and token bucket (tokens accumulate at a fixed rate up to a cap, each request consumes a token, naturally allows some burst while enforcing a long-run average rate — the most commonly used in production). For a distributed system, the limiter's state (the counter or bucket) needs to live somewhere shared — Redis with atomic increment operations is the standard choice — rather than in-process state that would let each server instance enforce its own independent limit.

**Q17. Design a distributed cache.**
Core mechanics: consistent hashing to distribute keys across cache nodes in a way that minimizes redistribution when nodes are added or removed (versus naive modulo hashing, where adding one node reshuffles almost every key's assigned node). Replication for availability, so losing one node doesn't lose that data entirely. An eviction policy (LRU is standard) for when the cache is full. And a defined consistency model between the cache and the underlying source of truth — write-through (write to cache and DB together, consistent but slower writes), write-back (write to cache first, asynchronously flush to DB, faster but riskier on cache failure), or cache-aside (application checks cache first, falls back to DB and populates cache on miss — the most common pattern in practice).

**Q18. Design a notification system that supports email, SMS, and push notifications at scale.**
Decouple notification *requests* from notification *delivery* via a message queue — the application publishes "notify user X via channel Y" events rather than calling delivery providers synchronously inline, which both smooths out load spikes and isolates the application from a slow or failing downstream provider. Separate worker pools per channel (email, SMS, push), since each has different rate limits, different provider APIs, and different failure characteristics from the others. Retry with exponential backoff for transient provider failures, with a dead-letter queue for messages that fail repeatedly, so they can be inspected rather than silently dropped. Idempotency keys on each notification request, so a retry (either yours or the provider's) doesn't result in the user receiving the same notification twice.

**Q19. Design a system to handle 1 million concurrent WebSocket connections.**
The core constraint is that each open WebSocket connection consumes server memory and a file descriptor, and a naive single-process server hits OS and hardware limits well before 1 million. Horizontal scaling across many connection-handling servers is required, with a load balancer distributing new connections across them. Since a message intended for a user might need to reach a connection held open on a different server than the one handling the request that triggered it, you need a pub/sub layer (Redis pub/sub, or a dedicated message broker) that all connection servers subscribe to, so any server can publish a message and it reaches the correct server holding that user's actual connection. Use an event-driven, non-blocking I/O model (not one thread per connection) on each server, since threads don't scale to hundreds of thousands of concurrent connections per machine the way an event loop does.

**Q20. Design a key-value store that needs to handle both high write throughput and strong consistency.**
This is fundamentally a CAIP-style trade-off conversation, and the interviewer wants to see you name it explicitly rather than pretend you can have everything for free. For strong consistency with high write throughput: a leader-based replication model, where all writes go through a single leader (ensuring a consistent, agreed-upon order) which then replicates to followers, using a consensus protocol (Raft or Paxos) to handle leader failure without losing consistency. Writes are only acknowledged once replicated to a quorum, not just the leader, trading some write latency for durability and consistency guarantees. If the interviewer pushes on scaling writes further, the honest next move is partitioning (sharding) the keyspace across multiple independent leader-follower groups, each handling a subset of keys — at which point you've traded some cross-partition transactional guarantees for horizontal write scalability, and saying that trade-off out loud is exactly the signal being tested for.

**Q21. Design a system for real-time analytics/dashboards over a high-volume event stream.**
Ingest events into a stream processing system (Kafka is the standard entry point) rather than writing directly to a database that would fall over under the write volume. A stream processor (Flink, or simpler windowed aggregation logic) computes rolling aggregates — counts, sums, rates over sliding time windows — incrementally as events arrive, rather than recomputing from raw event history on every dashboard refresh. Write the aggregated, pre-computed results to a fast read store optimized for the dashboard's actual query patterns (often a time-series database or a simple key-value store keyed by metric+window), decoupling the expensive continuous computation from the cheap, fast reads the dashboard actually needs. Accept eventual consistency — the dashboard reflects state as of a few seconds ago, not truly real-time to the millisecond — as the correct trade-off for this kind of system.

**Q22. Design an API rate-limiting and quota system for a public API with different pricing tiers.**
Layer the same rate-limiting mechanics (token bucket, most likely, for its natural burst tolerance) but parameterized per tier — each API key carries its tier, and the limiter looks up the tier-specific rate and burst limits at request time rather than having one global limit. Track both a short-term rate limit (requests per second/minute, protecting infrastructure from abuse) and a longer-term quota (requests per day/month, tied to the customer's actual paid plan) as two separate, independently-enforced mechanisms, since they serve different purposes and often have different reset semantics. Return clear, standard headers (remaining quota, reset time) on every response so API consumers can self-regulate rather than discovering the limit only by hitting a 429, and make the enforcement point a shared gateway/proxy layer rather than duplicated logic in every backend service.

## System Troubleshooting

**Q23. A production LLM application's latency has suddenly doubled. Walk through how you'd diagnose it.**
Check what actually changed first, since sudden regressions almost always have a specific trigger rather than gradual drift: a recent deploy, a provider-side model or infrastructure change, a traffic pattern shift, or a change in typical input/context length. Break down where the latency actually lives — time-to-first-token versus total generation time versus retrieval time versus network/queueing time — since "latency doubled" could mean any one of several very different underlying problems requiring different fixes. Check provider status pages and your own request logs for elevated error/retry rates, since retries on a flaky provider silently masquerade as pure latency increase. And check whether context length per request has grown (a corpus update producing longer average retrieved chunks, for instance), since generation latency scales with both input and output length.

**Q24. Users are reporting that an AI feature is giving inconsistent answers to the same question. How do you investigate?**
First establish whether "inconsistent" means genuinely different answers to literally identical input (expected to some degree with non-zero temperature, and the fix might simply be lowering temperature or increasing determinism for this specific use case) versus different answers to inputs the user perceives as identical but which actually differ subtly — different phrasing, different conversation history, different retrieved context due to an index that changed between the two calls. Log and compare the actual full prompts (not just the user-visible question) sent in both cases, since the discrepancy is very often visible there — a different set of retrieved chunks, a subtly different system prompt version if one was recently changed, or session/context state carried over unexpectedly from a prior turn.

**Q25. A model that was performing well in evaluation is producing poor-quality outputs in production. What do you check?**
Training-serving skew is the first suspect: confirm the exact preprocessing, prompt template, and feature computation used in production genuinely matches what was used during evaluation — a subtle mismatch here (different chunking logic, a prompt template edited after eval but not re-tested) is one of the most common root causes of this exact symptom. Check whether production input distribution has actually shifted from what the eval set represents — new types of user queries, a changed corpus, a different user population than was represented in the golden set — since a model can be genuinely excellent on the eval distribution while the production distribution has quietly moved away from it. And confirm you're actually running the model version you evaluated — a deployment or configuration mismatch serving a different model or prompt version than what was tested is a boring but disproportionately common explanation.
