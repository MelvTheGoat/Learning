
# Part 3: Fine-tuning, Evaluation, and ML Fundamentals

Evaluation is the section worth over-preparing. Every source in the compiled article agrees this is where most candidates fall apart, because it's the difference between "I called an LLM API" and "I know whether what I built actually works." Your RAG project's eval harness makes this section the one you should be strongest on, not the one you need to cram.

## Fine-tuning

**Q1. What is fine-tuning, and when do you actually need it instead of prompting?**
Fine-tuning continues training a pretrained model's weights on a smaller, task-specific dataset, changing what the model itself knows and how it behaves by default. Reach for it only after prompting and retrieval have genuinely plateaued: when you need a consistent output format or tone that prompting can't reliably enforce, when the task requires domain knowledge too specialized or too voluminous to fit in a prompt via RAG, when you need lower latency by using a smaller fine-tuned model instead of a larger general one, or when in-context examples alone aren't teaching the pattern reliably across edge cases. Fine-tuning is more expensive to build, slower to iterate on, and harder to debug than prompting — it should be a deliberate escalation, not a default.

**Q2. What's the difference between full fine-tuning and parameter-efficient fine-tuning (PEFT)?**
Full fine-tuning updates every parameter in the model, which requires storing full-precision gradients and optimizer states for the entire model — memory-intensive and expensive, and it fully overwrites the base model's weights, risking catastrophic forgetting of general capability. PEFT methods (LoRA being the dominant one) freeze the base model entirely and train only a small number of additional parameters injected into the architecture, dramatically reducing memory and compute cost while leaving the original model intact — you can even swap different LoRA adapters in and out of the same frozen base model for different tasks.

**Q3. What is LoRA and how does it work?**
Low-Rank Adaptation freezes the original weight matrices and, for each one you want to adapt, injects a pair of much smaller low-rank matrices whose product approximates the *change* needed to that weight, rather than retraining the weight itself. Because the rank is small (often 8–64, versus the original matrix's dimensions in the thousands), the number of trainable parameters drops by orders of magnitude — often under 1% of the full model — while performance on the target task approaches full fine-tuning in most practical cases. At inference, the low-rank update can be merged back into the original weights with zero added latency.

**Q4. What is QLoRA and why does it matter?**
QLoRA combines LoRA with 4-bit quantization of the frozen base model — the base weights are stored and computed in 4-bit precision instead of 16 or 32-bit, while the LoRA adapters themselves remain in higher precision for stable training. This shrinks the memory footprint enough that fine-tuning genuinely large models becomes feasible on a single consumer or prosumer GPU rather than requiring a multi-GPU cluster, which is the specific problem it was built to solve.

**Q5. What is instruction tuning?**
A fine-tuning stage, typically applied right after pretraining, where the model is trained on a dataset of instruction-response pairs specifically so it learns to follow directions and behave conversationally, rather than just continuing text in whatever style it was given. This is the step that turns a raw next-token-prediction model into something that reliably answers "summarize this" with a summary instead of continuing the sentence in some other direction — it's usually followed by RLHF or DPO to further align the model's response *style and preferences*, not just its instruction-following.

**Q6. What is catastrophic forgetting, and how do you prevent it during fine-tuning?**
When fine-tuning on a narrow dataset causes the model to lose general capabilities it had before — it gets very good at the new task and noticeably worse at everything else. Mitigations: use PEFT methods like LoRA, which touch far fewer parameters and are inherently less disruptive to the base model's broader knowledge; keep the learning rate low and use a small number of epochs, since aggressive training on a narrow dataset is exactly what causes forgetting; mix in some general-purpose data alongside the task-specific data during training; and always evaluate on both the target task *and* a held-out general benchmark, since forgetting is invisible if you only measure the metric you're optimizing.

**Q7. How much data do you actually need to fine-tune effectively?**
There's no universal number — it depends heavily on task complexity, how different the target behavior is from the base model's existing behavior, and which method you're using. As a rough guide: a few hundred high-quality, carefully curated examples can meaningfully shift behavior for a narrow, well-defined task, especially with PEFT; genuinely broad capability changes need thousands to tens of thousands. The much more important lever than raw volume is data quality and diversity — a small, clean, well-labeled dataset that actually covers the range of inputs you'll see in production consistently beats a large noisy one.

**Q8. How do you evaluate whether fine-tuning actually improved the model?**
The same evaluation harness discipline as everything else: a held-out test set the model never saw during training, scored on the actual target metric, compared directly against the base model's performance on the identical set. Critically, also evaluate on general capability benchmarks to check for catastrophic forgetting, and evaluate on edge cases and out-of-distribution inputs specifically, not just the distribution the fine-tuning data came from — a model can look dramatically better on in-distribution examples while quietly getting worse at everything slightly outside that distribution.

**Q9. What's the difference between SFT, RLHF, and DPO, and how do they fit together?**
Supervised Fine-Tuning trains directly on example input-output pairs — the most basic form, teaching the model what a good response looks like by direct demonstration. RLHF trains a separate reward model on human preference data (given two responses, which is better), then uses reinforcement learning to optimize the policy against that reward model — more complex and closer to directly optimizing for what humans actually prefer, but harder to train stably. DPO achieves a similar preference-alignment effect as RLHF but through a single, more stable supervised loss on preference pairs directly, skipping the separate reward model and RL loop. The typical pipeline is SFT first (teach basic instruction-following) then RLHF or DPO (align tone, safety, and preference).

**Q10. When would you fine-tune instead of using RAG, and when would you use both?**
Fine-tune when you need to change the model's *behavior* — style, format, reasoning pattern, tone — since that's not something retrieval can inject. Use RAG when you need the model to access *facts* — especially facts that change over time or that are too voluminous to bake into weights. They're not mutually exclusive: a common production pattern is fine-tuning a model to reliably follow a specific citation format and refuse appropriately, while RAG supplies the actual facts that model reasons over — fine-tuning shapes *how* it answers, RAG supplies *what* it answers with.

**Q11. What are common failure modes when fine-tuning goes wrong?**
Overfitting to the fine-tuning dataset's specific phrasing or narrow distribution, so the model performs beautifully on examples similar to training data and poorly on anything slightly different. Catastrophic forgetting of general capability. Learning spurious correlations in the training data that happen to correlate with the target label but aren't the actual signal (a classic version: if all your "urgent" examples happen to be short, the model learns "short = urgent" rather than the actual concept). And label noise or inconsistency in the training data itself silently capping how good the fine-tuned model can possibly get, regardless of how much compute you throw at training.

**Q12. How would you fine-tune a model to reliably produce a specific structured output format (e.g., a JSON schema)?**
In most cases you shouldn't need full fine-tuning for this at all — constrained decoding or grammar-based output constraints (forcing the model's token sampling to only produce tokens valid under a given schema) and function-calling APIs solve structured output reliably without touching the weights, and should be tried first. If those aren't available or don't fit the use case, fine-tune on a dataset of input/correctly-formatted-output pairs specifically, with the schema violations from earlier prompting attempts intentionally included as negative signal if you're using preference-based tuning, so the model learns not just the target format but specifically avoids the failure patterns it was previously prone to.

## Evaluation

**Q13. How do you build an evaluation framework for an LLM application from scratch?**
Start with a golden dataset — a curated, labeled set of representative inputs with known-good outputs or acceptance criteria, covering typical cases and deliberately including edge cases (out-of-scope, ambiguous, adversarial). Define metrics that match what actually matters for the task, not generic ones borrowed from a different problem. Automate scoring wherever possible — exact match or rule-based checks where the answer space is constrained, LLM-as-judge where it's open-ended — but validate any automated judge against human labels before trusting it. Wire the whole thing into CI so it runs on every change, with a defined threshold that fails the build on regression. And keep the framework versioned alongside the code, since an evaluation set that silently drifts out of sync with what the system actually does is worse than no evaluation at all.

**Q14. What is LLM-as-judge, and what are its real limitations?**
Using a (typically stronger) language model to score or compare outputs against criteria, instead of relying purely on exact-match rules or human review — necessary because most LLM outputs are open-ended text with no single correct string to match against. Limitations, stated plainly: judges have documented biases toward longer responses regardless of quality, toward responses stylistically similar to their own outputs, and toward the first option presented in pairwise comparisons unless you deliberately randomize position; judges can be inconsistent, producing different scores for the identical input across separate calls; and a judge is itself a model that can simply be wrong, especially on nuanced or highly domain-specific correctness that requires real expertise to assess. None of this makes LLM-as-judge useless — it makes it something that has to be validated, not trusted blindly.

**Q15. How do you validate that an LLM judge is actually trustworthy?**
Hand-label a representative sample yourself — or with a subject-matter expert — across the range of quality levels and categories you expect, then run the same items through the judge and compute agreement between the judge's labels and the human labels, typically via Cohen's kappa rather than raw percent agreement, since kappa corrects for the agreement you'd expect by chance. Below roughly 0.6 kappa, the judge shouldn't be trusted to report metrics you'd act on. Also test the judge's self-consistency — score the same item multiple times and check the variance — because a judge that disagrees with itself across repeated calls on identical input can't reasonably be expected to agree with a human rater either.

**Q16. What's the difference between offline and online evaluation?**
Offline evaluation runs against a fixed, static dataset before anything ships — golden sets, regression tests, benchmark suites — controlled, repeatable, and cheap to run repeatedly in CI, but necessarily limited to whatever cases you thought to include. Online evaluation measures real production behavior against real live traffic — user feedback signals (thumbs up/down, edits, corrections), A/B test outcomes, downstream business metrics — capturing the actual distribution of real usage including cases you never anticipated, but slower, noisier, and only observable after something has already shipped to real users. You need both: offline evaluation is your regression gate before shipping, online evaluation is how you find out what offline evaluation missed.

**Q17. What is a golden dataset, and how do you actually build one?**
A curated, labeled set of representative examples with known-correct answers or acceptance criteria, used as the stable reference for automated evaluation. Building one well: source real examples from actual usage where possible rather than only synthetic ones, since real user queries surface patterns you wouldn't think to construct; deliberately cover edge cases and known failure categories, not just typical happy-path examples — out-of-scope questions, negation, ambiguity, multi-step reasoning; label with enough care that you'd trust the labels to gate a production deployment, ideally with a second reviewer checking a sample for disagreement; and version it explicitly, since the dataset itself needs to evolve as new failure modes are discovered in production, with each version's results kept comparable.

**Q18. How do you evaluate when there's no single correct answer — for example, open-ended generation or creative tasks?**
Move from exact-match toward criteria-based scoring: define a rubric of specific properties the output must satisfy (grounded in the provided context, addresses the actual question asked, appropriate length and tone, no fabricated claims) and score against each criterion independently rather than a single holistic "good/bad" judgment, since a single number for an open-ended task hides which specific dimension is failing. Use an LLM judge scoped narrowly to one criterion at a time rather than one broad "rate this 1–10" prompt, since narrow, specific judging tasks are measurably more reliable than broad holistic ones. And for genuinely subjective quality dimensions, human evaluation on a sample remains the ground truth automated methods are ultimately validated against.

**Q19. What is groundedness (or faithfulness), and how do you measure it?**
Whether every factual claim in a generated answer is actually supported by the provided source context, as opposed to being introduced from the model's own parametric knowledge or invented outright. Measured by decomposing the answer into individual claims, then checking each claim against the retrieved source text — either via an LLM judge asked specifically "is this claim supported by this passage, yes or no" per claim, or via lexical/semantic overlap between the claim and the source as a cheaper proxy. This has to be measured separately from whether the answer is simply *correct*, since an answer can be factually true in the real world while being ungrounded in what was actually retrieved — which is still a failure, because it means the system got lucky rather than worked correctly.

**Q20. How do you evaluate for hallucination specifically?**
Distinguish two different things people conflate under "hallucination": factual incorrectness against the real world, and ungroundedness against the provided source context — a RAG system's job is really to prevent the second, since the first is a property of the model's training data the application layer can't fully control. Concretely: run groundedness scoring on every claim against retrieved context (as above), maintain a specific test set of questions designed to tempt fabrication (questions just outside the corpus's actual coverage, questions about plausible-sounding but nonexistent entities), and track a hallucination rate as a first-class metric over time, not just something checked once before initial launch.

**Q21. What's the difference between exact-match evaluation and semantic-similarity evaluation? When do you use each?**
Exact match checks whether the output equals a reference string precisely (or via simple normalization like case-folding) — fast, unambiguous, zero cost, but brittle: two answers can be equally correct while differing in exact wording, and exact match would score one of them as wrong. Semantic similarity (embedding cosine similarity, or an LLM judge assessing meaning-equivalence) tolerates paraphrase and rewording, better matching how "correct" actually works for open-ended text, but is noisier, more expensive, and can be fooled by superficially similar-sounding but substantively different answers. Use exact match for genuinely closed-form answers (classification labels, structured fields, numeric answers); use semantic evaluation for open-ended generation.

**Q22. How do you set up regression testing for prompts, so a prompt change doesn't silently break something else?**
Treat prompts as versioned code, not incidental config: every prompt change goes through the same golden-set evaluation suite before merging, with a defined threshold — if any metric drops beyond an acceptable margin (say, 2–5% depending on how much you trust the metric's own noise), the change is blocked. Run this in CI automatically on every pull request touching a prompt, not manually and not only occasionally. And version the prompts themselves alongside the golden set and the eval results, so you can trace exactly which prompt version produced which score, and roll back cleanly if a regression makes it through anyway.

**Q23. What is A/B testing for LLM features, and how does it differ from traditional A/B testing?**
The same fundamental structure as traditional A/B testing — randomly assign users to variant A or B, measure a business or engagement metric, and determine statistical significance — but with LLM-specific complications layered on top: outputs are non-deterministic even within one variant, so within-arm variance is higher than a typical traditional feature test, requiring larger sample sizes or longer run times to detect the same effect size; the "metric" is often itself derived from a judge or from indirect user behavior (did they accept the AI's suggestion, did they edit it, how long did they spend) rather than a clean binary conversion event; and cost per request varies by variant in a way traditional feature tests rarely have to account for, since one arm might be materially more expensive to run than the other even at identical traffic.

**Q24. How do you evaluate multi-turn conversations, as opposed to single-turn question answering?**
Single-turn metrics (groundedness, relevance, correctness) still apply per-turn, but multi-turn evaluation additionally needs to check conversational coherence across turns — does the system correctly use context from earlier in the conversation, does it contradict something it said two turns ago, does it correctly handle a user's follow-up that only makes sense given prior context (a pronoun referring back, a correction to an earlier statement). This typically means building golden multi-turn dialogues, not just golden single questions, and scoring the conversation as a trajectory rather than independently scoring each turn in isolation, since a turn that's locally fine can still be a failure in the context of the conversation so far.

**Q25. When do you need human evaluation despite having automated evals in place?**
When the automated judge's own validation (the kappa-against-human-labels check) shows insufficient agreement to trust it on a given dimension. When the quality dimension is genuinely subjective or requires domain expertise the judge model likely lacks — nuanced legal or medical correctness, for instance. Before any high-stakes launch, as a final sanity check that automated metrics haven't drifted from what actually matters to real users. And periodically, on a rolling sample even after launch, specifically to catch a scenario where the automated judge and reality have quietly diverged over time — automated evals can look stable while genuinely getting worse if the judge itself has a blind spot that production traffic has started to exploit.

**Q26. How do you measure calibration in LLM outputs, and why does it matter for evaluation?**
Calibration asks whether a model's expressed confidence matches its actual accuracy — if it says something with 90% apparent confidence, is it actually right about 90% of the time it says that. For LLMs this is harder than for classifiers with clean probability outputs, since raw next-token probabilities don't map cleanly to task-level correctness; common approaches include asking the model to explicitly output a confidence score and checking calibration of that self-reported number against ground truth, or using output entropy/log-probability of the response as a proxy signal. It matters because a well-calibrated "I don't know" is far more useful and far less dangerous than a confidently wrong answer, and calibration failures are specifically what allow a system to be both accurate-on-average and dangerously wrong on the tail.

**Q27. What is "vibes-based" evaluation, and how do you actually avoid falling into it?**
Judging model quality by manually trying a handful of prompts, eyeballing the outputs, and forming an impression — no structured dataset, no repeatable metric, no way to know if a later change actually improved or regressed anything. It's the default failure mode because it's fast and requires no infrastructure, and it's genuinely dangerous because it feels like real signal while providing almost none — a handful of manually-tried examples is a tiny, cherry-picked, non-representative sample, and human impression of "this looks better" is itself unreliable and inconsistent across even the same person on different days. The fix is exactly the evaluation harness discipline covered throughout this section: a real golden set, real metrics, run automatically, every time — this is the single most cited "what separates senior candidates" point across every source compiled into this question list.

**Q28. How would you evaluate a summarization system specifically?**
Groundedness/faithfulness first — does the summary contain any claim not actually supported by the source document, which is the single most common and most damaging summarization failure. Coverage — does the summary include the genuinely important points, not just any true subset of the source (a summary can be 100% faithful while omitting the one thing that actually mattered). Conciseness relative to information density, since a "summary" that's nearly as long as the source has failed at its basic job regardless of accuracy. And, if there's a reference summary available, ROUGE or similar overlap metrics as a cheap automated proxy — but these correlate only loosely with actual human judgment of summary quality, so they should supplement, not replace, faithfulness and coverage checks.

**Q29. How do you evaluate a system for safety and harmful content?**
Maintain a dedicated adversarial test set distinct from your normal golden set — prompts specifically designed to elicit harmful, biased, or policy-violating output, ideally including known jailbreak and prompt-injection patterns, updated as new attack patterns are discovered in the wild. Score against defined policy categories rather than a vague single "is this safe" judgment, since different harm categories need different detection approaches and different response strategies. Track both false negatives (harmful content that got through) and false positives (safe content incorrectly blocked or refused), since a system that's overly aggressive in refusing legitimate requests has a real cost too, not just a reputational one for over-refusal. And treat this as an ongoing red-teaming process, not a one-time pre-launch check — new attack patterns emerge continuously.

**Q30. What is inter-annotator agreement, and why does it matter for building an evaluation set?**
A measure of how consistently multiple independent human labelers agree when labeling the same data — typically computed with Cohen's kappa (two annotators) or Fleiss' kappa (more than two). It matters because if your own human labelers can't agree with each other on what the "correct" label is for a given example, that example's ground truth is inherently ambiguous, and no automated judge — however good — can be expected to hit a target that isn't itself well-defined. Low inter-annotator agreement on a category of question is a signal to either refine your labeling guidelines and definitions, or to accept that the category genuinely has no single correct answer and needs a different evaluation approach (rubric-based partial credit rather than binary correct/incorrect).

**Q31. How do you decide how large a golden evaluation set needs to be?**
Work backward from statistical power: how large an effect (a change in your metric) do you actually need to reliably detect, and how much run-to-run noise does your metric have at a given sample size — a small, noisy metric needs a much larger set to distinguish a real regression from ordinary variance. As a practical floor, tens of examples per distinct category you're tracking (not tens overall) is a reasonable minimum to say anything meaningful about that category specifically, since an aggregate score across 200 examples spread thinly across ten categories tells you almost nothing about any one category's actual performance. Report confidence intervals or variance alongside every metric, not just a bare point estimate, so "did this change actually matter" has an honest answer instead of a false sense of precision.

**Q32. How do you evaluate cost-quality tradeoffs when deciding between two models?**
Never compare on quality alone. Score both models on the identical golden set, with per-slice breakdown, not just an aggregate — then bring in cost per request (or per thousand requests) and p99 latency as co-equal dimensions of the decision, not afterthoughts. Plot or table the actual frontier: at what quality delta does the cheaper, faster model become the better production choice given your specific latency and budget constraints, rather than defaulting to "the highest-scoring model wins." A model that scores 2% higher but costs six times more and adds two seconds of latency is very often the wrong choice for production, even though it would "win" a quality-only comparison — and being able to say precisely why, with the actual frontier in hand, is what separates a real engineering decision from a benchmark screenshot.

## ML Fundamentals

**Q33. Explain the bias-variance tradeoff.**
Bias is error from a model being too simple to capture the true underlying pattern — it makes systematic, consistent errors regardless of what training data it sees (underfitting). Variance is error from a model being too sensitive to the specific training data it happened to see — it fits noise in the training set and generalizes poorly to new data (overfitting). The two trade off against each other as model complexity increases: a simple model has high bias, low variance; a highly flexible model has low bias, high variance. The goal is finding the complexity level that minimizes their sum — total generalization error — not minimizing either one alone.

**Q34. How do you detect and address overfitting versus underfitting?**
Detect by comparing training performance against validation performance: a large gap where training performance is much better than validation performance indicates overfitting; both being poor and similar indicates underfitting. For overfitting: regularization (L1/L2, dropout), more training data, simplifying the model, or early stopping based on validation loss. For underfitting: increase model capacity, add more relevant features, train longer, or reduce regularization strength if it's currently too aggressive.

**Q35. Explain precision and recall, and when you'd optimize for one over the other.**
Precision is, of the items the model flagged as positive, what fraction actually were positive — it answers "when the model says yes, how often is it right." Recall is, of all the actual positives that exist, what fraction did the model catch — it answers "of everything that should have been flagged, how much did we find." Optimize for precision when false positives are costly (flagging a legitimate transaction as fraud and blocking a real customer); optimize for recall when false negatives are costly (missing an actual case of fraud, or missing an actual tumor in a screening scan). Most real systems need to state this tradeoff explicitly and choose an operating point rather than pretending one metric alone captures what matters.

**Q36. What is cross-validation and why use it instead of a single train/test split?**
A technique for estimating how a model generalizes by repeatedly splitting the data into different train/validation partitions (k-fold being the standard: split into k parts, train on k−1, validate on the remaining one, rotate through all k), and averaging the resulting performance across all folds. This gives a more reliable, lower-variance estimate of true generalization performance than a single arbitrary split, which can be misleadingly lucky or unlucky depending on exactly which examples happened to land in the validation set. It's especially valuable with limited data, where a single held-out split would waste too much data or produce a noisy estimate.

**Q37. What's the difference between L1 and L2 regularization?**
Both penalize large model weights during training to reduce overfitting, but differently. L1 (Lasso) adds the sum of absolute weight values to the loss, which tends to push some weights all the way to exactly zero — producing sparse models and effectively performing automatic feature selection. L2 (Ridge) adds the sum of squared weight values, which shrinks all weights toward zero smoothly but rarely to exactly zero — it discourages any single feature from dominating without fully eliminating any of them. Use L1 when you suspect many features are irrelevant and want a sparse, more interpretable model; use L2 when you believe most features carry some signal and want to prevent any one from being overweighted.

**Q38. Explain gradient descent and the difference between its common variants (SGD, Adam, etc.).**
Gradient descent minimizes a loss function by repeatedly computing the gradient (direction of steepest increase) with respect to the model's parameters and stepping in the opposite direction, scaled by a learning rate. Batch gradient descent computes the gradient over the entire dataset per step — accurate but slow and memory-heavy for large datasets. Stochastic Gradient Descent (SGD) computes it on one example (or a small mini-batch) at a time — noisier updates, but much faster per step and often escapes shallow local minima better due to that noise. Adam adds per-parameter adaptive learning rates plus momentum (using running averages of both the gradient and its square), generally converging faster and more reliably than plain SGD with less manual learning-rate tuning, which is why it's the default choice for most deep learning training today.

**Q39. What is backpropagation, and why is it necessary for training neural networks?**
The algorithm for efficiently computing the gradient of the loss with respect to every parameter in a neural network, by applying the chain rule backward through the network's layers — computing the gradient at the output layer first, then propagating that gradient backward layer by layer, reusing intermediate computations rather than recomputing from scratch for every single parameter. Without it, computing gradients for a network with millions or billions of parameters individually would be computationally intractable; backpropagation makes it feasible by exploiting the network's layered structure to share computation.

**Q40. What is a confusion matrix, and what does each cell tell you?**
A table cross-tabulating a classifier's predictions against actual ground-truth labels. For binary classification: true positives (correctly predicted positive), true negatives (correctly predicted negative), false positives (predicted positive but actually negative — a Type I error), and false negatives (predicted negative but actually positive — a Type II error). Nearly every classification metric (precision, recall, F1, accuracy) is derived directly from these four counts, and looking at the raw matrix itself — not just a single summary metric — is often the fastest way to spot exactly which kind of error a model is systematically making.

**Q41. What's the difference between ROC-AUC and PR-AUC, and when do you prefer one?**
ROC-AUC plots true positive rate against false positive rate across all thresholds and summarizes the area under that curve — but the false positive rate is computed relative to the (often huge) number of true negatives, so under severe class imbalance ROC-AUC can look deceptively good even when the model is actually performing poorly on the minority positive class, because true negatives are so plentiful they swamp the metric. PR-AUC plots precision against recall instead, and since precision is directly sensitive to false positives relative to *predicted* positives (not the huge negative class), it's a much more honest signal under class imbalance — which is why fraud detection, rare disease screening, and similar rare-positive tasks favor PR-AUC over ROC-AUC as the headline metric.

**Q42. Why does feature engineering still matter in an era of large pretrained models?**
For unstructured data (text, images) where large pretrained models can learn strong representations directly from raw input, hand-engineering has genuinely diminished in importance. But most real production ML — fraud detection, credit risk, forecasting, recommendation — still runs on structured, tabular data where a well-designed feature (a ratio, a rolling statistic, a domain-specific flag capturing a known pattern) directly encodes domain knowledge no amount of raw data alone reliably discovers on its own, especially with limited training data. It also remains the primary lever for interpretability and for injecting knowledge about known business rules or physical constraints that a purely data-driven model has no way to know about.

**Q43. Why do you need separate train, validation, and test splits, and what's the specific risk of skipping one?**
Train is what the model actually learns from. Validation is used to tune hyperparameters and make model-selection decisions during development — critically, without touching the test set, so those decisions don't leak information from the final evaluation set into the choices you made. Test is touched exactly once, at the very end, to report a genuinely unbiased estimate of real-world performance. Skip the validation set and tune directly against the test set, and you've effectively fit your hyperparameters to the test set too — your reported "unbiased" test performance is now optimistic and will not hold up in production, because you've quietly used up the one thing that was supposed to stay untouched.

**Q44. What is data leakage, and what are its most common causes?**
When information that would not actually be available at prediction time in the real world sneaks into the training process, producing metrics that look excellent in development but collapse in production. Common causes: computing a feature using data from after the prediction timestamp (a rolling window that accidentally includes the current period); target leakage, where a feature is itself a proxy for or directly derived from the label (using "days until account was closed" to predict churn); preprocessing (scaling, imputation, encoding) fit on the full dataset including the test set, rather than fit only on training data and applied to test; and duplicate or near-duplicate records ending up split across both train and test sets, letting the model effectively memorize rather than generalize.

**Q45. How do you handle class imbalance in a classification problem?**
Several levers, usually combined rather than used alone: resampling (oversampling the minority class, undersampling the majority, or synthetic oversampling like SMOTE) to rebalance the training distribution; class weighting in the loss function, penalizing errors on the minority class more heavily without altering the actual data; choosing evaluation metrics that aren't misleading under imbalance in the first place (PR-AUC, precision/recall at a fixed operating point, rather than raw accuracy, which can look excellent by simply always predicting the majority class); and adjusting the decision threshold post-training rather than defaulting to 0.5, since the optimal threshold under imbalance is very often not 0.5. Worth noting explicitly: resampling techniques frequently improve ranking metrics while measurably damaging probability calibration, so recheck calibration after any resampling.

**Q46. Explain the difference between bagging and boosting as ensemble strategies.**
Bagging (bootstrap aggregating) trains many models independently and in parallel, each on a different random bootstrap sample of the training data, then averages (regression) or votes (classification) across them — this primarily reduces variance, since the independent models' errors partially cancel out. Random Forest is the canonical example. Boosting trains models sequentially, where each new model is trained specifically to correct the errors of the ensemble built so far, typically by up-weighting or targeting the residuals of previously misclassified examples — this primarily reduces bias, building up capacity incrementally, but is more prone to overfitting than bagging if not carefully regularized. XGBoost and LightGBM are boosting.

**Q47. What is the curse of dimensionality and how does it affect model training?**
As the number of features grows, the volume of the feature space grows exponentially, and the data needed to densely cover that space in order for distance-based or density-based methods to work well grows correspondingly — with a fixed dataset size, points become increasingly sparse and increasingly equidistant from each other in high dimensions, which specifically degrades algorithms that rely on meaningful distance (k-nearest-neighbors, clustering) and increases overfitting risk generally, since a model has more ways to fit noise when there are more dimensions to fit it in. Mitigations: dimensionality reduction (PCA and similar), feature selection to remove genuinely uninformative dimensions, and regularization to control the model's effective capacity relative to the dimensionality it's operating in.

**Q48. What's the difference between normalization and standardization, and does it matter which one you use?**
Normalization (min-max scaling) rescales features to a fixed range, typically [0, 1], preserving the original distribution's shape but compressing or stretching its range. Standardization (z-score scaling) rescales to zero mean and unit variance, without bounding the result to a fixed range, and is less sensitive to outliers dominating the scale than min-max normalization is. Which one matters depends on the downstream algorithm: distance-based methods (k-NN, k-means, SVMs with RBF kernels) and gradient-descent-optimized models generally need some form of scaling to perform well, since features on wildly different scales otherwise distort distance calculations or gradient step sizes; tree-based models (Random Forest, gradient boosting) are scale-invariant by construction and need neither.
